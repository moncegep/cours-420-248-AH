Au TP1, nous avons construit Dex sous forme d'application PHP classique, avec un rendu purement coté serveur : chaque clic rechargeait une page entièrement construite par le serveur.

Ce deuxième travail pratique (TP) reprend le même outil, mais répartit le travail entre trois parties :

- une **API** construite avec Express (Node.js). Elle est la seule couche qui communique avec la base de données ;
- un **site PHP** qui fournit le cadre commun des pages (en-tête, pied de page) et le routage ;
- une **interface Vue.js** qui affiche les données et gère les interactions utilisateur. C'est elle qui communique avec l'API.

Dans ce travail, **nous ajoutons également une page d'administration protégée** : elle permet à l'enseignant de se connecter pour modifier un travail et ses créneaux.

## Le scénario

Le scénario du TP1 ne change pas : chaque cours possède des travaux, chaque travail propose des créneaux, 
et les étudiants indiquent les créneaux où ils sont libres.
Dex met en évidence le ou les créneaux qui conviennent au plus grand nombre.

#### Changements et nouveautés

1. **L'expérience de l'étudiant** : 
    - Avant le filtrage des travaux, l'enregistrement d'une réponse et la mise à jour de la grille des disponibilités se se faisaient coté serveur (dans le PHP).
    - Maintenant, ça se fait sans rechargement de page, côté client via Vue.js.
2. **La mémoire de l'utilisateur courant** : 
   - Avant le matricule et le nom de l'étudiant étaient retenus dans une session PHP.
   - Maintenant elles sont retenus dans le navigateur, via `localStorage`
3. **L'administration (nouveau)** : 
   - L'enseignant peut se connecter pour modifier un travail (titre, description, dates, état ouvert ou fermé) et gérer ses créneaux.

{/* ### Mise en place

<Steps>

1. Dans le dossier `api/`, installez les dépendances avec `npm install`.
2. Copiez `.env.exemple` sous le nom `.env`. Ce fichier contient la configuration locale (port, accès à la base, origine du site). Il ne doit pas être remis : il figure déjà dans `.gitignore`.
3. Dans `bd.js`, créez un pool de connexions avec `mysql2/promise` à partir des variables du `.env`, chargées avec `dotenv`.
4. Dans `serveur.js`, créez l'application Express, activez `express.json()` pour lire les corps de requête en JSON, activez `cors()`, branchez vos routes, puis démarrez le serveur sur le port `PORT`.

</Steps>

<Aside type="note" title="Pourquoi cors() ?">
Pour un navigateur, une **origine** est la combinaison du protocole, du nom de domaine et du port. Le site PHP (`http://localhost`) et l'API (`http://localhost:3000`) n'ont donc pas la même origine. Par sécurité, un navigateur bloque dans bien des cas les réponses d'une autre origine, sauf si le serveur l'autorise explicitement. C'est le rôle du mécanisme **CORS** (*Cross-Origin Resource Sharing*).

Le paquet `cors` ajoute les en-têtes nécessaires. Limitez l'autorisation à l'origine du site :

```js
app.use(cors({ origin: process.env.ORIGINE_SITE }));
```
</Aside>

<Aside type="note" title="Les dates entre MySQL et JavaScript">
Par défaut, `mysql2` convertit les colonnes `DATE` et `DATETIME` en objets `Date` de JavaScript, qui sont ensuite envoyés en JSON dans le fuseau UTC. Une heure de 18 h peut alors s'afficher à 22 h. Pour éviter ce décalage, ajoutez `dateStrings: true` à la configuration du pool : les dates sont alors transmises telles qu'elles sont en base, par exemple `"2026-10-05 18:00:00"`.

En entrée, l'API accepte les dates au format produit par un champ `<input type="datetime-local">`, par exemple `"2026-10-05T18:00"`.
</Aside> */}

- En cas d'erreur, le corps a toujours la même forme : `{ "erreurs": ["Message 1", "Message 2"] }`.
- Les codes de statut HTTP suivants sont attendus.

Un **jeton** est une chaîne aléatoire que le serveur remet après une connexion réussie. Le client la renvoie ensuite avec chaque requête protégée, dans l'en-tête HTTP `Authorization` :

```text
Authorization: Bearer 3f1c9e2a-...
```

{/* Dans ce TP, le jeton est **opaque** : il ne contient aucune information, il sert seulement de clé. L'API le génère avec `crypto.randomUUID()` et le conserve en mémoire (par exemple dans un `Map`) avec l'`id` de l'utilisateur et l'heure d'expiration, fixée à 2 heures après la connexion. Redémarrer l'API efface donc tous les jetons, ce qui est acceptable ici. */}

{/* <Aside type="note" title="Et les JWT ?">
Dans de nombreuses applications, on utilise plutôt un JWT (*JSON Web Token*), un jeton signé qui contient lui-même ses informations. Ce mécanisme sera abordé plus loin dans la session. Le jeton opaque permet d'en comprendre d'abord le principe.
</Aside> */}

### Routes protégées

Chaque route suivante effectue ses vérifications dans cet ordre :

1. le jeton est présent, connu et non expiré (`401` sinon) ;
2. le travail ou le créneau visé existe (`404` sinon) ;
3. il appartient à un cours de l'enseignant connecté (`403` sinon) ;
4. les données reçues sont valides (`400` sinon).

<Aside type="note" title="Authentification et autorisation">
Les codes `401` et `403` répondent à deux questions différentes.  
L'**authentification** vérifie *qui* fait la requête (le jeton correspond-il à un enseignant ?).  
L'**autorisation** vérifie ce que cette personne a *le droit* de faire (ce travail est-il dans un de ses cours ?). 

Une requête peut donc être authentifiée et quand même refusée.
</Aside>

#### Règles de validation des routes d'administration :

- `titre` et `description` sont des chaînes de caractères non vides (le titre fait au plus 150 caractères) ;
- `type` est limité aux valeurs suivantes : `individuel` et `equipe` ;
- `disponible` est une date valide, `remise` une date et heure valide, et `remise` est postérieure à `disponible` ;
- `ouvert` est un booléen ;
- pour un créneau, `debut` et `fin` sont des dates et heures valides, et `fin` est postérieure à `debut` ;
- l'identifiant d'un nouveau créneau est généré par l'API sous la forme `<id du travail>-NN`, avec le prochain numéro libre sur deux chiffres (par exemple `web2-tp1-04`).

{/* <Aside type="tip" title="Vérifier le jeton : fonction ou middleware">
La façon la plus directe consiste à écrire une fonction, par exemple `utilisateurConnecte(req)`, qui lit l'en-tête `Authorization` et renvoie l'`id` de l'enseignant, ou `null` si le jeton est absent, inconnu ou expiré. Chaque route protégée l'appelle au début, répond `401` si elle obtient `null` et se sert ensuite de l'`id` pour vérifier le propriétaire du cours.

Vous pouvez aussi écrire un **middleware**, c'est-à-dire une fonction `(req, res, next)` qu'Express exécute avant la route : elle répond `401` ou conserve l'`id` dans `req.utilisateurId` et appelle `next()` pour laisser passer la requête. Ce choix est facultatif et ne donne pas de points supplémentaires.
</Aside> */}
{/* 
<Aside type="caution" title="Cacher une page ne protège rien">
La page `admin.php` est accessible à tous : n'importe qui peut l'ouvrir. La protection repose entièrement sur l'API. Une requête envoyée sans jeton, par exemple avec `curl -X DELETE http://localhost:3000/api/creneaux/web2-tp1-01`, doit recevoir `401` et ne rien supprimer. La même requête envoyée avec le jeton de `prof2` doit recevoir `403`, puisque `web2-tp1` appartient à un cours de `prof`.
</Aside> */}

## Site PHP

Le site PHP ne communique plus avec la base de données. Il fournit :

- **le cadre commun** : `includes/entete.php` (début du document, logo ou nom Dex menant à l'accueil, navigation vers l'accueil et l'administration) et `includes/pied.php` (nom de l'outil, votre nom, droits d'auteur), inclus dans chaque page ;
- **le routage gloabale** : une page PHP par écran (`index.php`, `travail.php`, `admin.php`), chacune avec son titre (`<title>`) et le point de montage de son application Vue ;
- **un rendu serveur minimal** : la page `travail.php` vérifie que l'identifiant du travail est une chaîne qui respecte le format `^[a-z0-9-]{1,30}$` et transmet l'identifiant à Vue dans un attribut, échappé avec `htmlspecialchars`
    - Si l'identifiant est absent ou mal formé, `travail.php` répond avec le code `404` (`http_response_code(404)`) et affiche le contenu de `404.php`, avec le même en-tête et le même pied de page.

<Aside type="note" title="Qui vérifie que le travail existe ?">
PHP vérifie seulement le **format** de l'identifiant. C'est l'API qui peut savoir si le travail existe en communiquant avec la base de données.
</Aside>

## Interface Vue.js

Vue êst chargé par **CDN** comme module JavaScript, sans étape de compilation :

```html
<script type="module" src="js/travail.js"></script>
```

### Exigences communes

- L'adresse de l'API est définie une seule fois, dans un fichier de config (`config.js`).
- Les appels à l'API sont regroupés dans un fichier `api.js`.

### Page d'un travail (`travail.php`)

- Après un enregistrement réussi, le matricule et le nom sont conservés dans `localStorage` (un espace de stockage du navigateur qui persiste après sa fermeture). À la visite suivante d'un travail, les champs sont préremplis et les créneaux déjà choisis par ce matricule sont cochés.

### Page d'administration (`admin.php`)

- Sans jeton valide, la page affiche un formulaire de connexion. Après une connexion réussie, le jeton est conservé dans `sessionStorage` (comme `localStorage`, mais effacé à la fermeture de l'onglet).
- Avant de supprimer un créneau, l'application demande une confirmation qui indique le nombre de réponses qui seront supprimées avec lui, par exemple : « Ce créneau a 3 réponses. Elles seront supprimées. Continuer ? ».

Créez un répertoire et invitez moi à la rejoindre (nom d'utilisateur: **`lelafontant`**).

Assurez vous d'avoir un `README.md` présente le projet et les fonctionnalités et qui explique : l'exécution de `init.sql`, l'installation et le démarrage de l'API, les comptes de démonstration.

## Éthique de travail

- **Travail régulier :** Vous devez faire au moins 5 commits significatifs par semaine.
- **Compréhension du code :** Vous devez être en mesure d'expliquer et justifier tout ce qui se trouve dans votre code. Une vérification pourra être fait à tout moment dans le projet.

<Aside type="caution" title='Pénalités'>
Un travail irrégulier ou des difficultés notables à expliquer son code se traduiront par une pénalité attribué au travail.
</Aside>
