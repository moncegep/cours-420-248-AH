À la fin du guide « Découper une page PHP en classes », `produits.php` ne contenait plus de SQL ni de `$_SESSION`. La page gardait pourtant trois rôles : elle **assemblait** ses objets, elle **enchaînait** les étapes de chaque opération, et elle **mêlait** ce traitement au HTML. Cette page les reprend un par un.

## Un service pour les cas d'usage

Ajouter un produit, c'est valider les données, construire l'entité, puis l'enregistrer. Tant que cet enchaînement vit dans `produits.php`, une API ou un script d'import qui voudrait ajouter un produit devra le réécrire, avec le risque d'en oublier une étape. Construire un produit sans l'avoir validé, par exemple, reste possible.

<Aside type="definition" title="Cas d'usage, service">
Un **cas d'usage** est une opération qu'un utilisateur peut demander au système : ajouter un produit, en retirer un, consulter le catalogue. Un **service** est un objet qui réunit des cas d'usage apparentés et en orchestre les étapes, en s'appuyant sur les entités, les dépôts et les validateurs. Il ne conserve rien d'un appel à l'autre.
</Aside>

Pour signaler des données refusées, le service lève une exception qui transporte les anomalies. C'est une classe comme une autre, qui hérite de la classe `Exception` fournie par PHP.

```php
<?php
// src/Service/DonneesInvalides.php
namespace App\Service;

use Exception;

class DonneesInvalides extends Exception
{
    public function __construct(private array $erreurs)
    {
        parent::__construct('Les données du produit sont invalides.');
    }

    public function getErreurs(): array
    {
        return $this->erreurs;
    }
}
```

<MarginNote type="rappel" titre="Lever, attraper">
`throw` interrompt l'exécution et remonte jusqu'au premier bloc `try` dont le `catch` correspond au type de l'exception. Les instructions situées entre les deux ne s'exécutent pas.
</MarginNote>

```php
namespace App\Service;

use App\Modele\Produit;
use App\Modele\ProduitRepository;
use App\Modele\ValidateurProduit;

class CatalogueService
{
    public function __construct(
        private ProduitRepository $depot,
        private ValidateurProduit $validateur
    ) {}

    /** @return Produit[] */
    public function lister(): array
    {
        return $this->depot->tous();

    {
        return $this->depot->trouver($id);
    }

    public function ajouter(array $donnees): Produit
    {
        $this->exigerValide($donnees);
        $id = $this->depot->ajouter($this->validateur->construire($donnees));

        return $this->validateur->construire($donnees, $id);
    }

    public function modifier(int $id, array $donnees): void
    {
        $this->exigerValide($donnees);
        $this->depot->modifier($this->validateur->construire($donnees, $id));
    }

    public function retirer(int $id): bool
    {
        return $this->depot->supprimer($id);

    private function exigerValide(array $donnees): void
    {
        $erreurs = $this->validateur->valider($donnees);

        if ($erreurs) {
            throw new DonneesInvalides($erreurs);
        }
    }
}
```

<Highlight couleur="ambre">Il n'est plus possible d'enregistrer un produit sans l'avoir validé : l'ordre des étapes appartient au service, plus à la page qui l'appelle.</Highlight>

Le service reçoit un simple tableau de données. Il ne lit pas `$_POST`, ne touche pas à la session et ne redirige personne. Rien en lui ne suppose qu'une page Web l'appelle, et c'est précisément ce qui le rend réutilisable par autre chose qu'une page Web.

<Aside type="caution" title="Pourquoi pas des méthodes statiques">
Il serait tentant d'écrire `CatalogueService::ajouter($donnees)`, sans créer d'objet. Le service devrait alors trouver lui-même son dépôt, le plus souvent dans une variable globale : la dépendance redevient invisible et impossible à remplacer, ce que l'injection avait justement réglé. Les méthodes statiques conviennent mieux à des fonctions qui ne dépendent de rien d'extérieur, comme une conversion de format.
</Aside>

## Assembler les objets en un seul endroit

Chaque page construisait ses propres objets, en répétant les mêmes `new` et les mêmes paramètres. 
On regroupe cette construction dans un fichier chargé en premier par toutes les pages.

<Aside type="definition" title="Fichier d'amorçage">
Fichier exécuté au début de chaque requête pour préparer l'environnement : chargement des classes, connexion, session, et construction des objets dont les pages ont besoin. C'est le seul endroit du programme qui choisit les classes concrètes et les relie entre elles.
</Aside>

```php
<?php
// bootstrap.php
use App\Modele\ProduitRepository;
use App\Modele\ValidateurProduit;
use App\Service\CatalogueService;
use App\Web\MessageFlash;

require_once __DIR__ . '/src/autoload.php';
require_once __DIR__ . '/includes/db.php';
require_once __DIR__ . '/includes/rendu.php';

session_start();

$categories = require __DIR__ . '/includes/categories.php';

$catalogue = new CatalogueService(
    new ProduitRepository($pdo),
    new ValidateurProduit($categories)
);

$flash = new MessageFlash();
```

Une page qui charge ce fichier dispose aussitôt de `$catalogue`, `$flash` et `$categories`, puisque `require` exécute le fichier dans sa propre portée. Remplacer le dépôt par une autre implémentation ne demanderait qu'une ligne, ici, et aucune dans les pages.

## Le modèle MVC

MVC répartit le code d'une application selon trois rôles, désignés par les initiales de leurs noms anglais.

- Le **modèle** porte les données et les règles : entités, dépôts, validateurs, services. Il ignore comment ses résultats seront affichés.
- La **vue** produit la présentation, ici du HTML, à partir de données qu'on lui fournit toutes prêtes. Elle ne décide de rien.
- Le **contrôleur** reçoit la requête, la traduit en appels au modèle, puis choisit la suite : afficher une vue, ou rediriger.

<Aside type="caution" title="Le modèle n'est pas la classe Produit">
Le mot « modèle » prête à confusion. En MVC, il désigne **toute la couche métier** : `CatalogueService`, `ProduitRepository`, `ValidateurProduit` et `Produit` ensemble. L'entité `Produit` n'en est qu'une partie. Réduire le modèle à l'entité conduit souvent à placer les règles métier dans le contrôleur, faute d'endroit prévu pour elles.
</Aside>

Le contrôleur de correction suit la même forme. Il se distingue par l'identification du produit, qui précède tout traitement.

```php
<?php
// produit-modifier.php : contrôleur
use App\Service\DonneesInvalides;

require_once __DIR__ . '/bootstrap.php';

$source = $_SERVER['REQUEST_METHOD'] === 'POST' ? $_POST : $_GET;
$id     = filter_var($source['id'] ?? '', FILTER_VALIDATE_INT);

if ($id === false) {
    http_response_code(400);
    rendre('produits/introuvable', ['titre' => 'Identifiant invalide']);
    exit;
}

$produit = $catalogue->trouver($id);

if ($produit === null) {
    http_response_code(404);
    rendre('produits/introuvable', ['titre' => 'Produit introuvable']);
    exit;
}

$erreurs = [];
$saisie  = [];

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    try {
        $catalogue->modifier($id, $_POST);
        $flash->deposer('Produit mis à jour.');
        header('Location: produits.php', true, 303);
        exit;
    } catch (DonneesInvalides $e) {
        $erreurs = $e->getErreurs();
        $saisie  = $_POST;
    }
}

rendre('produits/modifier', [
    'titre'      => 'Modifier un produit',
    'produit'    => $produit,
    'categories' => $categories,
    'erreurs'    => $erreurs,
    'saisie'     => $saisie,
]);
```

### Des vues qui ne voient que ce qu'on leur donne

Un contrôleur qui ferait simplement `require` de sa vue lui laisserait accès à toutes ses variables, `$catalogue` compris : rien n'empêcherait alors une vue d'interroger le service ou la base. Une petite fonction de rendu trace la frontière.

```php
<?php
// includes/rendu.php

/**
 * Affiche une vue en ne lui transmettant que les données fournies.
 */
function rendre(string $vue, array $donnees = []): void
{
    require_once __DIR__ . '/../vues/_aides.php';
    extract($donnees);
    require __DIR__ . '/../vues/' . $vue . '.php';
}
```

Une fonction a sa propre portée : les variables du contrôleur n'y existent pas. `extract()` crée une variable par clé du tableau, si bien que la vue dispose de `$produits`, `$message` ou `$erreurs`, et de rien d'autre.

Les vues partagent quelques fonctions d'affichage. Ce sont celles du guide sur la base de données, adaptées pour recevoir en paramètre ce qu'elles lisaient auparavant dans `$_POST`.

```php
<?php
// vues/_aides.php : fonctions réservées à l'affichage

function e(string $texte): string
{
    return htmlspecialchars($texte, ENT_QUOTES, 'UTF-8');
}

function prix(float $montant): string
{
    return number_format($montant, 2, ',', ' ') . ' $';
}

function valeur(array $saisie, string $champ, string $defaut = ''): string
{
    return e((string) ($saisie[$champ] ?? $defaut));
}

function messageErreur(array $erreurs, string $champ): string
{
    return isset($erreurs[$champ])
        ? '<p class="erreur">' . e($erreurs[$champ]) . '</p>'
        : '';
}
```

La vue de la liste ne contient plus que de l'affichage : des boucles, des conditions et des valeurs à écrire.

```php
<?php require __DIR__ . '/../gabarit/header.php'; ?>

<h2>Produits</h2>

<?php if ($message !== null): ?>
  <p class="message"><?= e($message) ?></p>

  </tr>

      <td><?= e($produit->getNom()) ?></td>

      </td>

  <?php endforeach; ?>
</table>

<h3>Ajouter un produit</h3>

  <label>
    Stock
```

<Aside type="syntaxe" title="La balise d'affichage courte">
`<?= expression ?>` est l'abréviation de `<?php echo expression; ?>`. Elle est très répandue dans les vues, où la plupart des balises PHP ne servent qu'à écrire une valeur.
</Aside>

La vue de correction reprend le même formulaire, en passant les valeurs actuelles du produit comme valeurs par défaut, par exemple `valeur($saisie, 'nom', $produit->getNom())`. La vue « introuvable » tient en quelques lignes.

```php
<?php require __DIR__ . '/../gabarit/header.php'; ?>

<h2><?= e($titre) ?></h2>
<p><a href="produits.php">Retour à la liste</a></p>

<?php require __DIR__ . '/../gabarit/footer.php'; ?>
```

<MarginNote type="rappel" titre="header.php et footer.php déménagent">
Ils produisent du HTML : leur place est désormais parmi les vues, dans `vues/gabarit/`, plutôt que dans `includes/`.
</MarginNote>

## Qui fait quoi

| | Contrôleur | Modèle | Vue |
| --- | --- | --- | --- |
| Lit `$_GET` et `$_POST` | oui | non, il reçoit des tableaux | non |
| Interroge la base | non, il passe par le service | oui, par le dépôt | non |
| Applique les règles métier | non | oui | non |
| Produit du HTML | non | non | oui |
| Redirige, dépose une confirmation | oui | non | non |

<Checkpoint question="Une vue exécute une requête SQL pour compter les produits en rupture. Le résultat s'affiche correctement. Qu'est-ce qui pose problème ?">
La vue prend une décision qui revient au modèle : elle connaît la table, ses colonnes et la définition d'une rupture. Le jour où cette définition change, par exemple pour tenir compte d'un seuil minimal, il faudra la retrouver dans une vue plutôt que dans le service. Le comptage gagne à devenir une méthode du service, appelée par le contrôleur, qui transmet le nombre à la vue.
</Checkpoint>

## Le gain : une deuxième sortie

Supposons qu'une application mobile doive ajouter des produits en envoyant du JSON. Voici, à titre d'illustration, tout ce qu'il faudrait écrire.

```php
<?php
// api/produits.php : un second contrôleur, qui répond en JSON
use App\Service\DonneesInvalides;

require_once __DIR__ . '/../bootstrap.php';

header('Content-Type: application/json');

try {
    $donnees = json_decode(file_get_contents('php://input'), true) ?? [];
    $produit = $catalogue->ajouter($donnees);

    http_response_code(201);
    echo json_encode(['id' => $produit->getId(), 'nom' => $produit->getNom()]);
} catch (DonneesInvalides $e) {
    http_response_code(422);
    echo json_encode(['erreurs' => $e->getErreurs()]);
}
```

<MarginNote type="astuce" titre="Trois nouveautés, pour mémoire">
`php://input` donne accès au corps brut de la requête, là où l'application mobile place son JSON. Le statut 201 signale une création réussie, le statut 422 des données comprises mais refusées.
</MarginNote>

Le service, le dépôt et le validateur servent **sans aucune modification**. Les règles métier ne sont écrites qu'une fois, et les deux sorties les appliquent à l'identique. Seul change ce qui relève de la présentation : du JSON au lieu du HTML.

## Quand ce découpage vaut l'effort

Pour un site de trois pages qui n'évolue plus, cette organisation coûte davantage qu'elle ne rapporte : une douzaine de fichiers au lieu de deux, et une requête qu'il faut suivre à travers cinq d'entre eux pour comprendre ce qu'elle fait.

Le bénéfice apparaît dans des situations assez précises :

- plusieurs écrans manipulent les mêmes données ;
- une deuxième sortie s'ajoute, comme une API ou un export ;
- les règles métier évoluent souvent, et doivent rester cohérentes partout ;
- plusieurs personnes travaillent sur le même code, l'une sur les vues, l'autre sur le modèle.

<Aside type="astuce" title="Ce que font les cadriciels">
Laravel et Symfony, les deux cadriciels PHP les plus répandus, fournissent cette organisation toute prête : chargement automatique, amorçage, contrôleurs, vues, et un routeur qui remplace le principe d'un contrôleur par fichier. Ce que cette page construit à la main correspond à ce qu'ils automatisent, ce qui rend leur fonctionnement bien plus lisible une fois ces notions acquises.
</Aside>

## Récapitulatif

- Un **service** réunit des cas d'usage et en garantit l'ordre des étapes. Il reçoit des tableaux, ignore le protocole Web, et devient réutilisable par une API comme par une page.
- Une **exception** dédiée, qui hérite de `Exception`, permet au service de refuser une opération en transportant les anomalies jusqu'au contrôleur.
- Le **fichier d'amorçage** est le seul endroit qui construit les objets et les relie. Les pages le chargent et utilisent ce qu'il prépare.
- En **MVC**, le modèle porte les données et les règles, la vue produit la présentation à partir de données prêtes, le contrôleur traduit la requête en appels au modèle et choisit la suite.
- Le mot **modèle** désigne toute la couche métier, pas seulement l'entité.
- Une **fonction de rendu** limite ce qu'une vue peut voir aux seules données transmises.
- Ce découpage devient rentable quand les écrans, les sorties, les règles ou les personnes se multiplient.
