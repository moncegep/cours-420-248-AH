Jusqu'à date, nous construisions des applications web complètent, mais fermés 
sur eux même. Grâce à la puissance de PHP, un script pouvait s'occuper de traiter 
la requête, se connecter à la base de données et formuler des requêtes, puis créer 
le contenu HTML dynamique.

Ici, nous voyons comment ouvrir son application à d'autres programmes, de façon 
organisée et prévisible. Ceci permettra de centraliser la logique métier et l'accès
aux données tout en laissant flexible l'exploitation et la présentation de ceux-ci.

## Pourquoi des API

<Aside type="definition" title="API">
Une **API**, pour *Application Programming Interface* (interface de programmation d'application), est l'ensemble des opérations qu'un logiciel met à la disposition d'autres logiciels, avec leurs entrées, leurs sorties et leurs règles d'usage. Le logiciel qui utilise l'API s'appelle le **client**.
</Aside>

### Ce qui motive une API

Revenons à notre exemple du catalogue de L'Érablière dorée. 
Nous avons construit un site web présentant ses produits, mais ce n'est pas nécessairement
le seule client qui pourrait présenter ou exploiter le catalogue.  
Une application mobile pourrait également afficher les produits, un partenaire pourrait vouloir les revendre, 
un script d'un administrateur système pourrait voiloir mettre les stocks à jour. 

Sans API, chacun devrait soit accéder directement à la base de données, 
soit extraire les données du HTML des pages, ce qui n'est pas commode. 
De plus, le moindre changement au niveau de la base de données ou dans le
rendu pourrait briser les clients.

Une API vient répondre à quelques besoins récurrents :

- **plusieurs clients** pour les mêmes données et les mêmes règles ;
- **des rythmes séparés** : le client et le serveur évoluent chacun de leur côté, parfois écrits par des équipes différentes, dans des langages différents ;
- **une seule mise en œuvre** des règles métier, au lieu d'une copie par client ;
- **exposer une capacité sans exposer l'implémentation** : le client n'a besoin de connaître ni la base, ni le code, ni l'organisation des fichiers.

### Une API est une interface

Dans les [notions avancées du POO](/cours/06-poo-2), on définissait une interface 
comme un contrat au niveau des classes qui énumère des méthodes, sans se fournir
leur implémentation (code). 

Une API est exactement cela, à l'échelle d'un système : elle énumère des opérations, 
leurs paramètres et leurs résultats, sans rien dire de la façon dont elles sont réalisées.

### Plusieurs sortes d'API

Le mot *API* désigne des choses de tailles très différentes.

| Sorte d'API | Exemple | Comment on l'utilise |
| --- | --- | --- |
| De bibliothèque ou de langage | les fonctions fournis par PHP comme `json_encode()`, l'API du DOM du navigateur | par un appel de fonction, dans le même programme |
| De système d'exploitation | ouvrir un fichier, lancer un processus | par un appel système, que le langage enveloppe |
| Web | un service de météo, de paiement, de cartographie | par des requêtes HTTP, à travers le réseau |

Parmi les API web, plusieurs styles coexistent: 
- Une API **REST**, présentée plus bas, organise tout autour de ressources désignées par des adresses. 
- **GraphQL** laisse le client décrire, dans une requête unique, la forme exacte des données qu'il veut recevoir. 
- Le style **RPC** consiste à appeler des procédures nommées à distance, comme `ajouterProduit`. 

Aucun n'est universellement supérieur ; REST reste le plus répandu pour les API publiques simples, et c'est lui que la suite de la page développe.

## L'architecture REST

<Aside type="definition" title="REST">
**REST**, pour *Representational State Transfer*, est un style d'architecture décrit par Roy Fielding en 2000. Ce n'est ni un protocole ni une norme, mais un ensemble de principes qui s'appuient sur HTTP.
</Aside>

Les principes REST (Representational State Transfer) décrivent un style architectural 
pour concevoir des systèmes distribués, notamment des API Web. 

REST définit plusieurs contraintes architecturales. Pour concevoir notre première API, nous en retiendrons principalement trois.

1. Communication client–serveur : le client gère principalement la présentation et les interactions; le serveur gère les ressources, les données et la logique associée. Cette séparation permet aux deux d'évoluer plus indépendamment.
2. Sans état (stateless) : chaque requête contient toute l'information nécessaire pour être comprise et traitée. Le serveur ne dépend pas d'un état de conversation conservé entre deux requêtes d'un même client.
3. Interface uniforme : les ressources sont manipulées suivant des conventions communes et prévisibles. C'est probablement la contrainte la plus importante de REST. Elle implique notamment :
    - l'identification des ressources, généralement par des URI;
    - la manipulation des ressources à travers leurs représentations (JSON, XML, etc.);
    - des messages suffisamment explicites pour être compris;
    - idéalement, des liens permettant au client de découvrir les actions ou ressources accessibles (HATEOAS).

<Aside type="caution" title="REST, ou à peu près">
Beaucoup d'API qui se disent REST n'en respectent qu'une partie. Ce n'est pas nécessairement un défaut : l'essentiel, pour un client, est que l'API soit cohérente et documentée. Les principes ci-dessus décrivent une cible raisonnable plutôt qu'un examen à réussir.
</Aside>

### Application à l'Érablière

Si nous appliquons REST au catalogue de l'Érablière, nous obtenons les cinq points d'accès suivants.

| Méthode | Adresse | Action | Réponse en cas de succès |
| --- | --- | --- | --- |
| `GET` | `/api/produits` | lister les produits | 200, la liste |
| `GET` | `/api/produits/7` | lire un produit | 200, le produit |
| `POST` | `/api/produits` | créer un produit | 201, le produit, et son adresse dans `Location` |
| `PUT` | `/api/produits/7` | remplacer un produit | 200, le produit modifié |
| `DELETE` | `/api/produits/7` | supprimer un produit | 204, sans corps |

Et quatre réponses d'erreur, chacune pour une raison distincte.

| Statut | Signification | Exemple |
| --- | --- | --- |
| 400 | la requête est illisible | le corps n'est pas du JSON valide |
| 404 | la ressource n'existe pas | `/api/produits/99`, ou `/api/clients` |
| 405 | la méthode ne convient pas à cette ressource | `DELETE /api/produits`, sur la collection entière |
| 422 | la requête est lisible, mais refusée | un prix négatif |

<Aside type="astuce" title="Nommer les ressources">
Quelques conventions répandues rendent une API prévisible : des noms plutôt que des verbes, au pluriel pour les collections, en minuscules, avec des traits d'union si le nom est composé. `/lignes-commande` se devine ; `/getLigneCommandeList` non.
</Aside>

<Checkpoint question="Pourquoi préférer DELETE /api/produits/7 à GET /api/supprimerProduit?id=7 ?">
Pour deux raisons. La première est la clarté du contrat : l'adresse désigne toujours la même ressource, et la méthode seule indique l'action, si bien qu'un client qui connaît `/api/produits/7` sait déjà comment la lire, la remplacer et la supprimer. La seconde est la sécurité, déjà rencontrée avec les formulaires : une requête GET peut être déclenchée sans intention, par un préchargement ou un robot, et ne devrait rien modifier.
</Checkpoint>

## Retour sur les superglobales

La [page sur les formulaires](/cours/04-formulaire) présentait `$_GET`, `$_POST` et `$_SERVER`. Une API en fait un usage différent, et l'une d'elles réserve une surprise.

- `$_SERVER['REQUEST_METHOD']` contient la méthode, quelle qu'elle soit : `PUT` et `DELETE` compris.
- `$_GET` contient les paramètres de la chaîne de requête, quelle que soit la méthode.
- `$_POST` n'est rempli que pour une requête `POST` **encodée comme un formulaire**. Un corps JSON, ou n'importe quel corps envoyé avec `PUT`, n'y apparaît pas.

<Highlight couleur="ambre">Pour une API qui reçoit du JSON, `$_POST` reste vide : le corps se lit ailleurs.</Highlight>

| Requête | `$_GET` | `$_POST` | `php://input` |
| --- | --- | --- | --- |
| `GET /api/produits?page=2` | `page` | vide | vide |
| `POST` d'un formulaire HTML | paramètres de l'adresse | les champs | le corps brut |
| `POST` avec un corps JSON | paramètres de l'adresse | vide | le JSON |
| `PUT` avec un corps JSON | paramètres de l'adresse | vide | le JSON |

Le corps brut d'une requête se lit par le flux `php://input`, puis se décode avec `json_decode()`.

```php
<?php
$corps   = file_get_contents('php://input');
$donnees = json_decode($corps, true);

if (!is_array($donnees)) {
    // corps absent, vide, ou JSON mal formé
}
```

<Aside type="syntaxe" title="Le second argument de json_decode">
Avec `true`, `json_decode()` rend des tableaux associatifs ; sans lui, il rend des objets. Les tableaux s'emploient comme `$_POST`, ce qui permet de transmettre les données au service sans rien changer à celui-ci.
</Aside>

<MarginNote type="rappel" titre="Une exception">
Pour un formulaire qui téléverse des fichiers, encodé en `multipart/form-data`, `php://input` reste vide : PHP a déjà réparti le contenu entre `$_POST` et `$_FILES`.
</MarginNote>

<Checkpoint question="Votre API reçoit un PUT avec un corps JSON correct, mais le code lit $_POST['nom'] et obtient une erreur. Pourquoi ?">
Parce que `$_POST` n'est rempli que pour un `POST` encodé comme un formulaire. Avec `PUT`, ou avec un corps JSON quelle que soit la méthode, le contenu reste dans le corps brut de la requête. Il faut le lire par `file_get_contents('php://input')`, puis le décoder avec `json_decode(..., true)`.
</Checkpoint>

## Créer l'API du catalogue

L'API réutilise tout ce qui existe déjà : le fichier d'amorçage, `CatalogueService`, le dépôt et le validateur. 
Elle s'organise comme une petite application Express : un routeur reçoit chaque requête, et la confie à l'action 
d'un contrôleur, qui reçoit deux objets, la requête et la réponse.

```text
erabliere/
├── api/
│   ├── .htaccess                      réécriture vers index.php
│   └── index.php                      point d'entrée unique : le routeur
├── src/
│   ├── Core/
│   │   ├── Request.php                la requête, comme req en Express
│   │   └── Response.php               la réponse, comme res en Express
│   ├── Controleur/
│   │   └── ProduitController.php      les actions sur les produits
│   └── …                              modèle et service, inchangés
└── …
```

### Trouver les classes

Le routeur utilise huit classes, réparties dans autant de fichiers. 
C'est le chargeur automatique, présenté dans la page sur les objets qui collaborent, 
qui permet à PHP de les trouver sans un `require_once` par fichier.

```php
<?php
// src/autoload.php

spl_autoload_register(function (string $classe): void {
    $prefixe = 'App\\';

    if (!str_starts_with($classe, $prefixe)) {
        return;
    }

    $relatif = substr($classe, strlen($prefixe));
    $fichier = __DIR__ . '/' . str_replace('\\', '/', $relatif) . '.php';

    if (is_file($fichier)) {
        require $fichier;
    }
});
```

La convention est la même pour toutes les classes : le nom complet reproduit le chemin du fichier, à partir de `src/`. 
`App\Core\Request` se trouve donc dans `src/Core/Request.php`, et `App\Controleur\ProduitController` dans `src/Controleur/ProduitController.php`. 
Ajouter une classe ne demande aucune ligne de plus dans le routeur, pourvu qu'elle respecte cette règle.

```php
<?php
// api/index.php : point d'entrée unique et routeur de l'API
use App\Controleur\ProduitController;
use App\Core\Request;
use App\Core\Response;
use App\Modele\ProduitRepository;
use App\Modele\ValidateurProduit;
use App\Service\CatalogueService;

require_once __DIR__ . '/../src/autoload.php';
require_once __DIR__ . '/../includes/db.php';

$catalogue = new CatalogueService(
    new ProduitRepository($pdo),
    new ValidateurProduit(require __DIR__ . '/../includes/categories.php')
);


$req      = new Request();
$res      = new Response();
$produits = new ProduitController($catalogue);

// Méthode, motif d'adresse, action
$routes = [
    ['GET',    'produits',      [$produits, 'lister']],
    ['POST',   'produits',      [$produits, 'creer']],
    ['GET',    'produits/{id}', [$produits, 'afficher']],
    ['PUT',    'produits/{id}', [$produits, 'remplacer']],
    ['DELETE', 'produits/{id}', [$produits, 'supprimer']],
];

$permises = [];

foreach ($routes as [$methode, $motif, $action]) {
    // {id} devient un groupe nommé qui n'accepte que des chiffres
    $regex = '#^' . preg_replace('#\{(\w+)\}#', '(?P<$1>\d+)', $motif) . '$#';

    if (!preg_match($regex, $req->path, $trouve)) {
        continue;
    }

    if ($methode !== $req->method) {
        $permises[] = $methode;
        continue;
    }

    $req->params = array_filter($trouve, 'is_string', ARRAY_FILTER_USE_KEY);
    $action($req, $res);
    exit;
}

if ($permises) {
    $res->methodNotAllowed($permises);
} else {
    $res->notFound('Ressource introuvable.');
}
```

<Aside type="syntaxe" title="Du motif à l'expression régulière">
`preg_replace()` remplace chaque `{nom}` du motif par un groupe nommé qui n'accepte que des chiffres : 
`produits/{id}` devient l'expression `#^produits/(?P<id>\d+)$#`. 
Quand elle correspond, `preg_match()` range la valeur trouvée sous la clé `id`, que le routeur recopie 
dans `$req->params`. Une adresse comme `produits/abc` ne correspond à aucune route, d'où un 404 sans code supplémentaire.
</Aside>

Le routeur ne sait rien des produits, et le contrôleur ne sait rien des adresses : 
ajouter une ressource revient à écrire un contrôleur et à déclarer ses routes. 
Ni l'un ni l'autre ne contient de règle métier ; tout cela reste dans le service, 
que les pages HTML et l'API partagent désormais.

```php
public function creer(Request $req, Response $res): void
{
    if (!$req->hasJsonBody) {
        $res->badRequest('Le corps de la requête doit être un objet JSON.');
        return;
    }

    try {
        $produit = $this->catalogue->ajouter($req->body);
    } catch (DonneesInvalides $e) {
        $res->unprocessable($e->getErreurs());
        return;
    }

    $res->status(201)
        ->header('Location', 'produits/' . $produit->getId())
        ->json($this->versTableau($produit));
}
```

```php
public function remplacer(Request $req, Response $res): void
{
    $id = (int) $req->params['id'];

    if ($this->catalogue->trouver($id) === null) {
        $res->notFound('Produit introuvable.');
        return;
    }

    if (!$req->hasJsonBody) {
        $res->badRequest('Le corps de la requête doit être un objet JSON.');
        return;
    }

    try {
        $this->catalogue->modifier($id, $req->body);
    } catch (DonneesInvalides $e) {
        $res->unprocessable($e->getErreurs());
        return;
    }

    $res->json($this->versTableau($this->catalogue->trouver($id)));
}
```

```php
private function versTableau(Produit $produit): array
{
    return [
        'id'        => $produit->getId(),
```

```php
            ->json($this->versTableau($produit));

    {

            $res->badRequest('Le corps de la requête doit être un objet JSON.');
            return;

            $this->catalogue->modifier($id, $req->body);
        } catch (DonneesInvalides $e) {

            return;
```

### La requête et la réponse

Plutôt que de lire `$_SERVER` ou `php://input` et d'appeler `header()` un peu partout, 
le routeur construit deux objets et les transmet à l'action. 
La **requête** rassemble ce que le client a envoyé ; la **réponse** offre des méthodes pour répondre, qui s'enchaînent.

```php
<?php

namespace App\Core;

/**
 * Requête HTTP, dans l'esprit de l'objet req d'Express.
 *
 * Corrections par rapport à la version d'origine :
 *  - path est relatif au dossier du point d'entrée : « produits/7 », et non
 *    « erabliere/api/produits/7 » ;
 *  - un corps JSON mal formé, ou qui n'est pas un objet, ne provoque plus
 *    d'erreur de type : body reste vide et hasJsonBody vaut false, ce qui
 *    permet au contrôleur de répondre 400.
 */
class Request
{
    public string $method;
    public string $path;
    public array $params = [];
    public array $query = [];
    public array $body = [];
    public array $headers = [];

    /** Vrai si le corps de la requête contenait un objet JSON lisible. */
    public bool $hasJsonBody = false;

    /**
     * @param string|null $base dossier du point d'entrée ; déduit de
     *                          SCRIPT_NAME s'il n'est pas fourni
     */
    public function __construct(?string $base = null)
    {
        $this->method  = $_SERVER['REQUEST_METHOD'];
        $this->query   = $_GET;
        $this->headers = function_exists('getallheaders') ? getallheaders() : [];

        // Chemin demandé, débarrassé du dossier qui contient le point d'entrée
        $chemin = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH) ?? '';
        $base ??= rtrim(str_replace('\\', '/', dirname($_SERVER['SCRIPT_NAME'])), '/');

        if ($base !== '' && str_starts_with($chemin, $base)) {
            $chemin = substr($chemin, strlen($base));
        }
        $this->path = trim($chemin, '/');

        // Corps : absent, objet JSON lisible, ou contenu inexploitable
        $donnees = json_decode(file_get_contents('php://input'), true);

        if (is_array($donnees)) {
            $this->body = $donnees;
            $this->hasJsonBody = true;
        }
    }
}
```

```php
<?php

namespace App\Core;

/**
 * Réponse HTTP, dans l'esprit de l'objet res d'Express.
 *
 * Corrections par rapport à la version d'origine :
 *  - header() permet de poser un en-tête, comme Location ou Allow ;
 *  - json() précise le jeu de caractères et conserve les accents ;
 *  - sendStatus() n'écrit plus de corps parasite : il envoie le statut seul ;
 *  - les réponses d'erreur utilisent les clés « erreur » et « erreurs ».
 */
class Response
{
    private int $statusCode = 200;
    private bool $sent = false;

    public function status(int $code): self
    {
        $this->statusCode = $code;
        http_response_code($code);
        return $this;
    }

    public function header(string $name, string $value): self
    {
        header("$name: $value");
        return $this;
    }

    public function send(string $content): void
    {
        if ($this->sent) return;
        echo $content;
        $this->sent = true;
    }

    public function json(mixed $data): void
    {
        if ($this->sent) return;
        header('Content-Type: application/json; charset=utf-8');
        echo json_encode($data, JSON_UNESCAPED_UNICODE);
        $this->sent = true;
    }

    public function redirect(string $url, int $statusCode = 302): void
    {
        if ($this->sent) return;
        header("Location: $url", true, $statusCode);
        $this->sent = true;
    }

    /** Envoie un statut sans corps, par exemple 204 après une suppression. */
    public function sendStatus(int $code): void
    {
        if ($this->sent) return;
        $this->status($code);
        $this->sent = true;
    }

    public function isSent(): bool
    {
        return $this->sent;
    }

    public function badRequest(string $message = 'Requête invalide.'): void
    {
        $this->status(400)->json(['erreur' => $message]);
    }

    public function unauthorized(string $message = 'Authentification requise.'): void
    {
        $this->status(401)->json(['erreur' => $message]);
    }

    public function forbidden(string $message = 'Accès refusé.'): void
    {
        $this->status(403)->json(['erreur' => $message]);
    }

    public function notFound(string $message = 'Ressource introuvable.'): void
    {
        $this->status(404)->json(['erreur' => $message]);
    }

    /** 405 : la ressource existe, mais pas pour cette méthode. */
    public function methodNotAllowed(array $allowed): void
    {
        $this->status(405)
            ->header('Allow', implode(', ', $allowed))
            ->json(['erreur' => 'Méthode non prise en charge.']);
    }

    /** 422 : données lisibles, mais refusées ; anomalies indexées par champ. */
    public function unprocessable(array $erreurs): void
    {
        $this->status(422)->json(['erreurs' => $erreurs]);
    }

    public function internalServerError(string $message = 'Erreur interne du serveur.'): void
    {
        $this->status(500)->json(['erreur' => $message]);
    }

    public function error(string $message, int $code = 400): void
    {
        $this->status($code)->json(['erreur' => $message]);
    }
}
```

<MarginNote type="rappel" titre="Des méthodes qui s'enchaînent">
`status()` et `header()` rendent l'objet lui-même (`return $this`), ce qui permet d'écrire `$res->status(201)->header('Location', …)->json(…)` sur une seule instruction. `json()` et `sendStatus()`, qui terminent l'échange, ne rendent rien.
</MarginNote>

Qui connaît Express retrouvera chaque élément.

| Express | Cette API | Rôle |
| --- | --- | --- |
| `req.method` | `$req->method` | la méthode HTTP |
| `req.path` | `$req->path` | le chemin, sans le dossier de l'API |
| `req.params.id` | `$req->params['id']` | un paramètre extrait de l'adresse |
| `req.query` | `$req->query` | la chaîne de requête |
| `req.body` | `$req->body` | le corps JSON décodé |
| `res.status(201).json(obj)` | `$res->status(201)->json($obj)` | un statut, puis un corps JSON |
| `res.set('Location', url)` | `$res->header('Location', $url)` | poser un en-tête |
| `res.sendStatus(204)` | `$res->sendStatus(204)` | un statut seul |
| `app.get('/produits/:id', h)` | `['GET', 'produits/{id}', $h]` | déclarer une route |

<Aside type="syntaxe" title="Le rôle d'express.json()">
En Express, `req.body` n'est rempli que si l'intergiciel `express.json()` a lu et décodé le corps. Ici, c'est le constructeur de `Request` qui s'en charge : il lit `php://input`, décode le JSON, et note dans `hasJsonBody` si le corps contenait bien un objet.
</Aside>

### Un point d'entrée unique avec .htaccess

Une API REST pose un problème que les pages n'avaient pas. L'adresse `/api/produits/7` ne correspond à aucun fichier : il n'existe pas de dossier `produits` contenant un fichier `7`. La page sur les services et MVC avait volontairement évité tout routage, en faisant de chaque fichier un contrôleur. Ici, ce n'est plus possible : l'adresse désigne une ressource, pas un fichier, et il faut un code qui l'interprète.

La solution consiste à confier toutes les requêtes adressées à l'API à un seul fichier, `api/index.php`, qui décompose l'adresse lui-même. C'est le serveur Apache qui s'en charge, grâce à un fichier de configuration.

<Aside type="definition" title=".htaccess, réécriture d'adresse">
Un fichier `.htaccess` contient des directives de configuration qu'Apache applique au dossier où il se trouve et à ses sous-dossiers, sans avoir à redémarrer le serveur. La **réécriture d'adresse** transforme, avant tout traitement, l'adresse demandée en une autre : le navigateur demande `/api/produits/7`, Apache exécute `index.php`.
</Aside>

```apache
# api/.htaccess
RewriteEngine On

# Les fichiers et dossiers qui existent réellement sont servis tels quels
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d

# Tout le reste est confié à index.php
RewriteRule ^ index.php [L]
```

Ligne par ligne :

- `RewriteEngine On` active la réécriture pour ce dossier.
- Les deux `RewriteCond` limitent la règle aux adresses qui ne désignent ni un fichier (`!-f`) ni un dossier (`!-d`) existants.
- `RewriteRule` capture tout ce qui suit `api/` dans `$1` et le transmet à `index.php`.

<Aside type="caution" title="Vérifier XAMPP">
Deux conditions doivent être réunies pour qu'Apache lise ce fichier. Le module de réécriture doit être chargé : dans `httpd.conf`, la ligne `LoadModule rewrite_module modules/mod_rewrite.so` ne doit pas être commentée. Et le dossier doit autoriser les `.htaccess` : `AllowOverride All` pour `htdocs`. XAMPP est généralement configuré ainsi, mais un 404 d'Apache sur `/api/produits` indique le plus souvent que l'une des deux manque. Une erreur 500 signale plutôt une faute de frappe dans le `.htaccess`.
</Aside>

<MarginNote type="rappel" titre="Propre à Apache">
Un `.htaccess` n'est lu que par Apache. Le serveur intégré de PHP, `php -S`, l'ignore ; on lui passe plutôt le point d'entrée en argument : `php -S localhost:8000 -t . api/index.php`. Nginx utilise sa propre configuration.
</MarginNote>

#### Un autre usage : interdire un dossier

Le même mécanisme protège les dossiers qui n'ont pas à être servis directement. Les classes de `src/` ou la connexion de `includes/db.php` n'ont pas à être accessibles par une adresse.

```apache
# src/.htaccess et includes/.htaccess
Require all denied
```

Apache répond alors 403 à toute demande visant ces dossiers, tandis que PHP continue de les charger normalement par `require`.


## Récapitulatif

- Une **API** met les opérations d'un logiciel à la disposition d'autres logiciels. Elle permet plusieurs clients, des rythmes d'évolution séparés et une seule mise en œuvre des règles.
- Elle applique à l'échelle d'un système les principes déjà vus pour les classes : encapsulation, **couplage faible**, responsabilité unique. Une API est une interface : le client dépend de ce qu'elle promet, pas de la façon dont elle le tient.
- Une API web se conçoit en répondant à une série de questions : adresse, méthode, format, en-têtes, statuts, erreurs, authentification, **CORS**, versionnement, documentation.
- **REST** organise l'API autour de ressources désignées par des adresses ; la méthode HTTP porte l'action, chaque requête se suffit à elle-même, et le code de statut dit le résultat.
- `$_POST` ne reçoit que les `POST` encodés comme des formulaires. Un corps JSON se lit par `php://input`, puis `json_decode(..., true)`.
- Un **.htaccess** confie à Apache la réécriture des adresses vers un point d'entrée unique, qui interprète la route et répond.
- Le point d'entrée agit comme un **routeur** : il construit une requête et une réponse, à la manière d'Express, et confie chaque couple méthode et adresse à l'action d'un **contrôleur**, qui s'appuie sur le service.
