Jusqu'ici, nous avons construis des applications web complètent, mais fermés 
sur eux même. Ici, nous voyons comment ouvrir son application à d'autres programmes, de façon 
organisée et prévisible. Ceci permettra de centraliser la logique métier et l'accès
aux données tout en laissant flexible l'exploitation et la présentation de ceux-ci.

On change également d'outil pour construire les APIs: **l'API sera écrite en JavaScript, avec Node.js et Express**.


## Pourquoi des API

<Aside type="definition" title="API">
Une **API**, pour *Application Programming Interface* (interface de programmation d'application), 
est l'ensemble des opérations qu'un logiciel ou système met à la disposition d'autres logiciels.
L'API précise leurs entrées, leurs sorties et leurs règles d'usage.  
Le logiciel qui utilise l'API s'appelle le **client**.
</Aside>

### Ce qui motive une API

Revenons à notre exemple du catalogue de *L'Érablière dorée*. 
Nous avons construit un site web présentant ses produits, mais ce n'est pas nécessairement
le seule client qui pourrait présenter ou exploiter le catalogue.

#### Autres clients potentiels

- Une application mobile pourrait également afficher les produits
- un partenaire pourrait vouloir les revendre, 
- un script d'un administrateur système pourrait voiloir mettre les stocks à jour. 

Sans API, chacun devrait soit accéder directement à la base de données, 
soit extraire les données du HTML des pages, ce qui n'est pas commode. 
De plus, le moindre changement au niveau de la base de données ou dans le
rendu pourrait briser les clients.

#### Une API vient répondre à quelques besoins récurrents

- **plusieurs clients** pour les mêmes données et les mêmes règles ;
- **des rythmes séparés** : le client et le serveur évoluent chacun de leur côté, parfois écrits par des équipes différentes, dans des langages différents ;
- **une seule mise en œuvre** des règles métier, au lieu d'une copie par client ;
- **exposer une capacité sans exposer l'implémentation** : le client n'a besoin de connaître ni la base, ni le code, ni l'organisation des fichiers.

{/* ### Une API est une interface

Dans les [notions avancées du POO](/cours/06-poo-2), on définissait une interface 
comme un contrat au niveau des classes qui énumère des méthodes, sans se fournir
leur implémentation (code). 

Une API est exactement cela, à l'échelle d'un système : elle énumère des opérations, 
leurs paramètres et leurs résultats, sans rien dire de la façon dont elles sont réalisées. */}

### Plusieurs sortes d'API

Le mot *API* désigne des choses de tailles très différentes.

| Sorte d'API | Exemple | Comment on l'utilise |
| --- | --- | --- |
| De bibliothèque ou de langage | les fonctions fournis par PHP comme `json_encode()`, l'API du DOM du navigateur | par un appel de fonction, dans le même programme |
| De système d'exploitation | ouvrir un fichier, lancer un processus | par un appel système, que le langage enveloppe |
| Web | un service de météo, de paiement, de cartographie | par des requêtes HTTP, à travers le réseau |

Parmi les API web, plusieurs styles coexistent: 
- Une API **REST**, présentée plus bas, organise tout autour de ressources désignées par des adresses. 
- **GraphQL** laisse le client décrire, dans une requête unique, la forme exacte des données qu'il veut recevoir. 
- Le style **RPC** consiste à appeler des procédures nommées à distance, comme `ajouterProduit`. 

Aucun n'est universellement supérieur ; REST reste le plus répandu pour les API publiques simples, et c'est lui que la suite de la page développe.

## L'architecture REST

<Aside type="definition" title="REST">
**REST**, pour *Representational State Transfer*, est un style d'architecture. 
Ce n'est ni un protocole ni une norme, mais un ensemble de principes qui s'appuient 
sur le protocole HTTP.
</Aside>

Les principes REST décrivent un style architectural 
pour concevoir des systèmes distribués, notamment des API Web. 

REST définit plusieurs contraintes architecturales. Pour concevoir notre première API, nous en retiendrons principalement trois.

1. **Communication client–serveur** : le client gère principalement la présentation et les interactions; le serveur gère les ressources, les données et la logique associée. Cette séparation permet aux deux d'évoluer plus indépendamment.
2. **Sans état (stateless)** :chaque requête contient toute l'information nécessaire pour être comprise et traitée. Le serveur ne dépend pas d'un état de conversation conservé entre deux requêtes d'un même client.
3. **Interface uniforme** : les ressources sont manipulées suivant des conventions communes et prévisibles. C'est probablement la contrainte la plus importante de REST. Elle implique notamment :
    - l'identification des ressources, généralement par des URI;
    - la manipulation des ressources à travers leurs représentations (JSON, XML, etc.);
    - des messages suffisamment explicites pour être compris;
    - idéalement, des liens permettant au client de découvrir les actions ou ressources accessibles (HATEOAS).

{/* <Aside type="caution" title="REST, ou à peu près">
Beaucoup d'API qui se disent REST n'en respectent qu'une partie. Ce n'est pas nécessairement un défaut : l'essentiel, pour un client, est que l'API soit cohérente et documentée. Les principes ci-dessus décrivent une cible raisonnable plutôt qu'un examen à réussir.
</Aside> */}

### Application de REST à l'Érablière

Si nous appliquons REST au catalogue de l'Érablière, nous obtenons les cinq points d'accès suivants.

| Méthode | Adresse | Action | Réponse en cas de succès |
| --- | --- | --- | --- |
| `GET` | `/api/produits` | lister les produits | 200, la liste |
| `GET` | `/api/produits/7` | lire un produit | 200, le produit |
| `POST` | `/api/produits` | créer un produit | 201, le produit, et son adresse dans `Location` |
| `PUT` | `/api/produits/7` | remplacer un produit | 200, le produit modifié |
| `DELETE` | `/api/produits/7` | supprimer un produit | 204, sans corps |

Et quatre réponses d'erreur, chacune pour une raison distincte.

| Statut | Signification | Exemple |
| --- | --- | --- |
| 400 | la requête est illisible | le corps n'est pas du JSON valide |
| 404 | la ressource n'existe pas | `/api/produits/99`, ou `/api/clients` |
| 405 | la méthode ne convient pas à cette ressource | `DELETE /api/produits`, sur la collection entière |
| 422 | la requête est lisible, mais refusée | un prix négatif |

<Aside type="astuce" title="Nommer les ressources">
Quelques conventions répandues rendent une API prévisible : des noms plutôt que des verbes, au pluriel pour les collections, en minuscules, avec des traits d'union si le nom est composé. `/lignes-commande` se devine ; `/getLigneCommandeList` non.
</Aside>

<Checkpoint question="Pourquoi préférer DELETE /api/produits/7 à GET /api/supprimerProduit?id=7 ?">
Pour deux raisons. La première est la clarté du contrat : l'adresse désigne toujours la même ressource, et la méthode seule indique l'action, si bien qu'un client qui connaît `/api/produits/7` sait déjà comment la lire, la remplacer et la supprimer. La seconde est la sécurité, déjà rencontrée avec les formulaires : une requête GET peut être déclenchée sans intention, par un préchargement ou un robot, et ne devrait rien modifier.
</Checkpoint>

### Préparer le projet

Node.js s'installe depuis `nodejs.org`, en version LTS (*Long Term Support*, la version maintenue le plus longtemps). 
XAMPP n'intervient pas ici : Node.js est lui-même le serveur.


<Aside type="definition" title="Node.js, npm, Express">
**Node.js** est un environnement qui exécute du JavaScript en dehors du navigateur, par exemple sur un serveur. **npm** est son gestionnaire de paquets : il télécharge les bibliothèques dont un projet dépend et les range dans le dossier `node_modules`. **Express** est l'une de ces bibliothèques : un cadriciel minimal pour écrire des serveurs web et des API avec Node.js.
</Aside>


```bash
mkdir erabliere-api
cd erabliere-api
npm init -y                  # crée package.json
npm install express          # télécharge Express
```

<Aside type="definition" title="package.json">
Fiche d'identité d'un projet Node.js : son nom, ses dépendances et leurs versions, et des scripts à lancer. `npm install` y inscrit chaque paquet installé. Le dossier `node_modules` se reconstruit à partir de ce fichier ; on ne le copie pas et on ne le remet pas avec un travail.
</Aside>

Deux ajouts au `package.json` créé par `npm init` :

```json
{
  "name": "erabliere-api",
  "version": "1.0.0",
  "type": "module",
  "main": "src/serveur.js",
  "scripts": {
    "dev": "node --watch src/serveur.js",
    "start": "node src/serveur.js"
  },
  "dependencies": {
    "express": "^5.3.0"
  }
}
```

- `"type": "module"` permet d'écrire `import` et `export`, la syntaxe des modules qu'on retrouvera avec Vue.js.
- Le script `dev` lance le serveur avec `--watch` : Node.js le redémarre à chaque modification d'un fichier. On le lance par `npm run dev`.

<Aside type="definition" title="Module">
En JavaScript, un **module** est un fichier qui choisit ce qu'il rend disponible avec `export`, et qui obtient ce dont il a besoin avec `import`. Le reste de son contenu lui demeure privé. C'est l'équivalent, en plus strict, des fichiers PHP inclus avec `require`.
</Aside>

<MarginNote type="rappel" titre="Deux syntaxes de modules">
Beaucoup d'exemples en ligne utilisent encore `require()` et `module.exports`. C'est l'ancienne syntaxe de Node.js, nommée CommonJS. Elle fonctionne toujours, mais ne se mélange pas facilement avec `import`.
</MarginNote>

### Un premier serveur

```js
// src/serveur.js : une première version, remplacée plus bas
import express from 'express';

const app = express();

app.get('/api/bonjour', (req, res) => {
  res.json({ message: 'Bonjour du catalogue' });
});

app.listen(3000, () => {
  console.log('Serveur prêt : http://localhost:3000/api/bonjour');
});
```

- `express()` crée l'**application**, qui recevra toutes les requêtes.
- `app.get(adresse, fonction)` déclare une **route** : pour une requête `GET` à cette adresse, Express appelle la fonction avec deux objets, la requête `req` et la réponse `res`.
- `res.json()` convertit l'objet en JSON, pose l'en-tête `Content-Type: application/json` et envoie la réponse.
- `app.listen(3000)` ouvre le port 3000 et attend les requêtes.

<Aside type="caution" title="Un serveur qui reste en marche">
En PHP, chaque requête lance l'exécution d'un script, qui se termine avec la réponse : rien ne survit d'une requête à l'autre, d'où les sessions et la base de données. Avec Node.js, c'est **un seul programme** qui démarre, puis qui reste en marche et traite toutes les requêtes. Une variable déclarée hors des routes est donc partagée par toutes les requêtes, et par tous les clients. Elle disparaît seulement quand le serveur s'arrête.
</Aside>

<Checkpoint question="Le serveur tourne. Vous modifiez le message de la route, sans utiliser --watch, puis vous rechargez la page. Pourquoi voyez-vous encore l'ancien message ?">
Parce que le programme a lu le fichier au démarrage, et qu'il continue de s'exécuter avec cette version. En PHP, chaque requête relit le fichier, d'où l'effet immédiat d'une modification. Avec Node.js, il faut redémarrer le serveur ; l'option `--watch` le fait automatiquement à chaque enregistrement.
</Checkpoint>

## Créer l'API du catalogue

L'API offre les cinq points d'accès définis plus haut. Elle se construit en trois étapes, chacune motivée par les limites de la précédente :

1. les cinq points d'accès, dans un seul fichier ;
2. la vérification de ce que le client envoie ;
3. l'organisation du code avec un routeur.

Pour se concentrer sur Express, l'API garde ses produits dans un tableau en mémoire, plutôt que dans la base MySQL utilisée par les pages.

### Étape 1 : les cinq points d'accès

Tout tient dans un seul fichier, `src/serveur.js`.

```text
erabliere-api/
├── package.json
├── node_modules/        créé par npm install
└── src/
    └── serveur.js       les données, les cinq routes et le démarrage
```

Express offre, pour la requête et la réponse, tout ce dont l'API a besoin.

| Express | Rôle |
| --- | --- |
| `app.get(adresse, fonction)`, `app.post(…)`, `app.put(…)`, `app.delete(…)` | déclarer une route pour une méthode et une adresse |
| `req.params.id` | la partie de l'adresse désignée par `:id`, toujours sous forme de texte |
| `req.body` | le corps JSON de la requête, déjà décodé |
| `res.status(404)` | choisir le code de statut ; se combine avec la suite |
| `res.json(objet)` | envoyer l'objet en JSON |
| `res.location(adresse)` | poser l'en-tête `Location` |
| `res.sendStatus(204)` | envoyer un statut seul, sans corps |

Par défaut, Express ne lit pas le corps d'une requête. La ligne `app.use(express.json())`, placée avant les routes, lui demande de lire le JSON reçu et de le ranger dans `req.body`.

```js
// Permet de lire un corps JSON dans req.body
app.use(express.json());

// Les produits, gardés en mémoire tant que le serveur tourne
const produits = [
  { id: 1, nom: "Sirop d'érable doré 540 ml",  categorie: 'sirop',      prix: 14.5,  stock: 12 },
  { id: 2, nom: "Sirop d'érable ambré 540 ml", categorie: 'sirop',      prix: 15.25, stock: 7 },
  { id: 3, nom: "Beurre d'érable 250 g",       categorie: 'tartinade',  prix: 9.95,  stock: 0 },
  { id: 4, nom: "Gelée d'érable 190 ml",       categorie: 'tartinade',  prix: 11,    stock: 9 },
  { id: 5, nom: 'Tire sur la neige',           categorie: 'confiserie', prix: 6.25,  stock: 30 },
  { id: 6, nom: 'Coffret découverte',          categorie: 'coffret',    prix: 39,    stock: 5 },
];
let prochainId = 7;

// GET /api/produits : la liste
app.get('/api/produits', (req, res) => {
  res.json(produits);
});

// GET /api/produits/:id : un produit
app.get('/api/produits/:id', (req, res) => {
  const produit = produits.find((p) => p.id === Number(req.params.id));
  if (!produit) {
    return res.status(404).json({ erreur: 'Produit introuvable.' });
  }
  res.json(produit);
});

// POST /api/produits : créer un produit
app.post('/api/produits', (req, res) => {
  const { nom, categorie, prix, stock } = req.body;
  const produit = { id: prochainId++, nom, categorie, prix, stock };
  produits.push(produit);
  res.status(201).location(`/api/produits/${produit.id}`).json(produit);
});

// PUT /api/produits/:id : remplacer un produit
app.put('/api/produits/:id', (req, res) => {
  const produit = produits.find((p) => p.id === Number(req.params.id));
  if (!produit) {
    return res.status(404).json({ erreur: 'Produit introuvable.' });
  }
  const { nom, categorie, prix, stock } = req.body;
  Object.assign(produit, { nom, categorie, prix, stock });
  res.json(produit);
});

// DELETE /api/produits/:id : supprimer un produit
app.delete('/api/produits/:id', (req, res) => {
  const position = produits.findIndex((p) => p.id === Number(req.params.id));
  if (position === -1) {
    return res.status(404).json({ erreur: 'Produit introuvable.' });
  }
  produits.splice(position, 1);
  res.sendStatus(204);
});

app.listen(3000, () => {
  console.log('API du catalogue : http://localhost:3000/api/produits');
});
```

<Aside type="syntaxe" title="return res.status(…)">
Envoyer une réponse ne termine pas la fonction. Sans `return`, l'exécution continuerait après le 404, et tenterait d'envoyer une seconde réponse : Express signalerait alors l'erreur « Cannot set headers after they are sent ». Le `return` placé devant `res.status(…).json(…)` envoie la réponse et quitte la fonction d'un même geste.
</Aside>

<Aside type="caution" title="req.params.id est du texte">
Dans `/api/produits/7`, `req.params.id` vaut `'7'`, une chaîne. Or `'7' === 7` est faux. D'où le `Number(req.params.id)` avant chaque comparaison. Une adresse comme `/api/produits/abc` donne `NaN`, qui n'est égal à aucun identifiant : la réponse est un 404, sans code supplémentaire.
</Aside>

<Aside type="caution" title="Des données qui ne durent pas">
Le tableau vit dans la mémoire du serveur. Les modifications sont visibles par tous les clients tant que le serveur tourne, mais elles disparaissent à chaque redémarrage, y compris ceux que provoque `--watch` à chaque enregistrement. C'est acceptable pour apprendre Express ; ce ne l'est pas pour un vrai catalogue. Une page suivante remplacera ce tableau par la base MySQL.
</Aside>

#### Mettre l'étape 1 à l'épreuve

Les requêtes prévues fonctionnent. Mais une API ne choisit pas ses clients : n'importe quel programme peut lui envoyer n'importe quoi. Voici ce que répond l'étape 1 à quatre requêtes moins sages.

| Requête | Réponse de l'étape 1 |
| --- | --- |
| `POST` avec `{"nom": "Pastilles"}` | 201 : un produit sans catégorie, sans prix ni stock, est créé |
| `POST` avec un prix de `-3` et la catégorie `fromage` | 201 : le produit est créé tel quel |
| `POST` sans corps | 500, et une page d'erreur HTML : `req.body` vaut `undefined`, et la route plante |
| `POST` avec `{"nom":` | 400, mais sous forme de page HTML, illisible pour un programme |

<Highlight couleur="ambre">L'étape 1 croit tout ce que le client lui envoie.</Highlight>

<Checkpoint question="Les pages HTML du catalogue avaient des champs obligatoires et un champ de prix numérique. Pourquoi ces protections ne suffiraient-elles pas pour l'API ?">
Parce qu'elles vivent dans le formulaire, donc chez le client. Une API ne reçoit pas ses requêtes d'un formulaire qu'elle a elle-même produit : elle les reçoit de `curl`, d'un script, d'une application ou d'une page écrite par d'autres. La seule vérification sur laquelle le serveur peut compter est la sienne. C'était déjà vrai pour les pages, où un formulaire modifié dans le navigateur contourne les attributs `required`.
</Checkpoint>

### Étape 2 : vérifier ce que le client envoie

Les quatre requêtes de l'épreuve révèlent deux sortes de problèmes, qui appellent deux statuts différents :

- **400** : le corps est absent, illisible, ou n'est pas un objet JSON. L'API ne peut même pas lire la demande.
- **422** : le corps est un objet lisible, mais ses valeurs sont refusées : nom vide, catégorie inconnue, prix négatif. L'API répond avec les anomalies par champ, sous la clé `erreurs`.

Deux fonctions s'ajoutent en tête du fichier, après les données. Les règles sont celles du guide sur la base de données.

```js
const categories = ['sirop', 'tartinade', 'confiserie', 'coffret'];

// Vrai si le corps de la requête est un objet JSON (et non un tableau, ou rien)
```

### Étape 3 : organiser avec un routeur

L'API fonctionne et est encore maintenable. Cependant, `serveur.js` compte déjà 125 lignes, et plusieurs signes montrent qu'il ne tiendra pas longtemps ainsi.

- **Il fait quatre choses à la fois** : il garde les données, applique les règles, déclare les routes et démarre le serveur. Chacune est une raison distincte de le modifier.
- **Les adresses se répètent** : `'/api/produits'` est écrit deux fois, `'/api/produits/:id'` trois fois. Renommer la ressource, ou la placer sous `/api/v1`, demande de modifier chaque route.
- **La prochaine ressource s'y mêlera** : les commandes, proposées en exercice plus bas, ajouteraient leurs routes et leurs règles au même fichier.

<Aside type="definition" title="Routeur">
Un **routeur** Express est un ensemble de routes regroupées dans un module, à la manière d'une petite application. On le branche ensuite sur un **préfixe** d'adresse avec `app.use()`. Les adresses déclarées dans le routeur sont relatives à ce préfixe.
</Aside>

Le changement tient en peu de lignes :

```js
// Avant, dans serveur.js
app.get('/api/produits/:id', (req, res) => { /* … */ });

// Après, dans routes/produits.js
const router = Router();
router.get('/:id', (req, res) => { /* … */ });
export default router;

// Et dans app.js, une seule fois pour toutes les routes des produits
app.use('/api/produits', router);
```

Le préfixe n'est plus écrit qu'une fois. 


<Aside type='tip' title="Simplifier l'écriture des points d'accès">
Un routeur offre en plus `router.route(adresse)`, qui regroupe toutes les méthodes d'une même adresse.
```js
router.route('/:id')
  .get((req, res) => { /* … */ })
  .put((req, res) => { /* … */ })
  .delete((req, res) => { /* … */ })
  .all((req, res) => {
    res.set('Allow', 'GET, PUT, DELETE').status(405).json({ erreur: 'Méthode non prise en charge.' });
  });
```

Il se termine par `.all()` pour les méthodes non prévues : c'est là que se place le 405.
</Aside>

```js
app.use(express.json());

// Toutes les adresses qui commencent par /api/produits vont au routeur des produits
app.use('/api/produits', produits);

// Aucune route n'a répondu : 404 en JSON
app.use((req, res) => {
  res.status(404).json({ erreur: 'Ressource introuvable.' });
});

// Corps JSON illisible (400) ou erreur imprévue (500)
app.use((err, req, res, next) => {
  if (err.type === 'entity.parse.failed') {
    return res.status(400).json({ erreur: "Le corps de la requête n'est pas du JSON valide." });
  }
  console.error(err);
  res.status(500).json({ erreur: 'Erreur interne du serveur.' });
});

export default app;
```

<Aside type='caution' title="L'ordre de déclaration est important">
Express examine les `app.use()` et les routes dans l'ordre où ils sont déclarés.

L'ordre a donc un sens :

- `express.json()` vient avant le routeur, sans quoi `req.body` serait vide au moment où les routes le lisent.
- Le 404 vient après le routeur : il n'est atteint que si aucune route n'a répondu.
- La fonction de gestion d'erreurs vient en dernier, comme à l'étape 2.
</Aside>

## Exercice : la ressource des commandes

Ajoutez à l'API une seconde ressource, les commandes, en suivant l'organisation des produits : un module de données `src/donnees/commandes.js`, un routeur `src/routes/commandes.js`, branché dans `app.js` sur `/api/commandes`.

Une commande a la forme suivante :

```json
{
  "id": 1,
  "client": "Ana Tremblay",
  "lignes": [
    { "produitId": 2, "quantite": 3 },
    { "produitId": 5, "quantite": 1 }
  ],
  "total": 52
}
```

| Méthode | Adresse | Réponse en cas de succès | Erreurs |
| --- | --- | --- | --- |
| `GET` | `/api/commandes` | 200, la liste | |
| `GET` | `/api/commandes/:id` | 200, la commande | 404 |
| `POST` | `/api/commandes` | 201, la commande et son adresse dans `Location` | 400, 422 |
| `DELETE` | `/api/commandes/:id` | 204 | 404 |

#### Règles à respecter :

1. Le client envoie seulement `client` et `lignes`. Le serveur attribue l'identifiant et **calcule le total** à partir des prix des produits.
2. `client` est obligatoire. `lignes` est un tableau non vide ; chaque ligne désigne un produit existant, avec une quantité entière d'au moins 1. Toute anomalie produit un 422, avec les clés `client` ou `lignes` dans `erreurs`.
3. Toute autre méthode répond 405, avec l'en-tête `Allow`.

## Récapitulatif

- Une **API** met les opérations d'un logiciel à la disposition d'autres logiciels. Elle permet plusieurs clients, des rythmes d'évolution séparés et une seule mise en œuvre des règles.
- Elle applique à l'échelle d'un système les principes déjà vus pour les classes : encapsulation, **couplage faible**, responsabilité unique. Une API est une interface : le client dépend de ce qu'elle promet, pas de la façon dont elle le tient.
- Une API web se conçoit en répondant à une série de questions : adresse, méthode, format, en-têtes, statuts, erreurs, authentification, **CORS**, versionnement, documentation.
- **REST** organise l'API autour de ressources désignées par des adresses ; la méthode HTTP porte l'action, chaque requête se suffit à elle-même, et le code de statut dit le résultat.
- **Node.js** exécute du JavaScript sur le serveur ; un seul programme reste en marche et traite toutes les requêtes. **Express** fournit le routage et les objets `req` et `res`.
- `express.json()` décode le corps JSON dans `req.body` ; `req.params` contient les parties variables de l'adresse, sous forme de texte.
- Une API ne choisit pas ses clients : elle vérifie elle-même ce qu'elle reçoit. Un corps illisible ou absent mérite un **400** ; des valeurs refusées, un **422**, avec les anomalies par champ.
- Un **routeur** regroupe les routes d'une ressource ; `app.js` le branche sur un préfixe, puis traite les cas restants : 404, puis les erreurs. `router.route()` regroupe les méthodes d'une adresse, et `.all()` répond 405 aux autres.
